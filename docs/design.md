# ReSocket 设计说明

## 要解决的问题

行情、IM 这类高频推送场景都建在 WebSocket 长连接上。OkHttp 提供了连接本身，但一条"能在生产环境用的长连接"还需要：

- 心跳：弱网下 TCP 连接会"半开"，本端以为连着，实际早已不通，没有任何错误回调。
- 重连：断开后自动连回来，间隔要退避，不能在服务端故障时雪上加霜。
- 订阅恢复：重连后服务端不记得之前订阅过什么，客户端要自己补发。
- 背压：行情一秒几百条，UI 处理不过来时要有明确的丢弃策略，不能无限堆积，也不能卡住读线程。
- 线程：OkHttp 的回调在它自己的读线程上，业务要的是能在任意协程里收集的 Flow。

每个团队都在重复写这些，而且很容易写错：重连和手动断开的竞态、旧连接迟到的回调、订阅和连接成功之间的时序、
取消收集时忘了退订。这个库把它们一次做对。

## 不做的事

- 不理解任何具体协议。订阅消息长什么样、消息属于哪个 topic、心跳发什么，都由接入方通过配置告诉库。
- 不解析消息。下游拿到的是原始字符串，用什么 JSON 库是接入方的事。
- 不缓存发送失败的消息。未连接时 `send` 返回 false；对交易指令这类消息，延迟送达比送达失败更危险。
- 不监听网络状态。库提供 `reconnectNow()`，什么时候调用（网络恢复、回到前台）由接入方决定。

## 公开 API

```kotlin
public interface ReSocket : Closeable {
    public val state: StateFlow<ConnectionState>
    public val messages: Flow<String>

    public fun connect()
    public fun disconnect()
    public fun reconnectNow()

    public fun subscribe(subscription: Subscription, backpressure: Backpressure? = null): Flow<String>
    public fun send(text: String): Boolean
}
```

## 关键决定

### 订阅的生命周期就是 Flow 的收集周期

`subscribe()` 返回冷流：开始收集时订阅，取消收集时退订。同一个 topic 有多个收集者时只向服务端订阅一次，
最后一个离开才退订。调用方不需要记得"退订"这件事，协程作用域结束（页面销毁、ViewModel 清理）订阅就自动释放，
不会因为漏掉退订而让服务端一直推没人要的数据。

断线期间 Flow 不结束也不报错，只是没有数据；重连成功后库补发订阅消息。
需要感知断线的场景（比如重建本地订单簿）观察 `state`。

### 状态只在一个协程里修改

连接状态、重连计数、订阅表只在一个协程里读写。调用方的操作、OkHttp 的回调、定时器到期都变成一条命令排进队列逐条处理。
好处：

- 不需要锁，也就没有锁顺序的问题。
- 时序自然成立：订阅消息一定在连接成功之后、按注册顺序发出；`disconnect()` 之后到达的"连接成功"一定被忽略。
- 状态机可以用假的传输层和虚拟时间做确定性测试，不需要真实网络和 sleep。

每次发起连接会递增一个代数（generation），回调带着自己的代数，和当前代数不一致就丢弃。
这解决了"旧连接迟到的失败回调把新连接拖进重连"这类问题。

### 消息分发不走命令队列

消息频率比状态变化高几个数量级，走队列会让每条行情多一次线程切换。
分发直接发生在 OkHttp 的读线程上，只读两个 `@Volatile` 的不可变快照（topic 到收集者的映射、全量收集者列表），
订阅变化时由状态协程整体替换。

### topic 由接入方从消息里取

`topicOf: (String) -> String?` 每条消息调用一次，结果用来查表分发，和订阅数量无关。
另一种做法是每个订阅带一个 `matches(message)` 谓词，那样每条消息要被所有订阅各判断一次，每次判断很可能都要解析一遍 JSON。

### 背压：每个收集者独立缓冲，不提供"挂起"

每个收集者有自己的 Channel，一个慢的收集者不会影响其他人。
策略有 `dropOldest`（默认，容量 64）、`dropNewest`、`latest`、`unbounded`。

没有"挂起发送方"：发送方是 OkHttp 的读线程，挂起它等于停止读 socket，pong 也收不到，连接会被判死。
不能丢消息的场景用 `unbounded`，并自己保证收集者跟得上。

丢弃通过 `MessagesDropped` 事件上报，同一个 topic 每秒最多一次，带上期间丢弃的条数。
逐条上报的话，监听器本身会成为高频场景下的瓶颈。

### 心跳判活看"有没有数据进来"

应用层心跳发出后，超时时间内收到任何数据都算连接活着，不要求是特定的 pong。
行情推送本身就能证明连接是通的，库也不需要理解各家的 pong 格式。
只认心跳发出之后收到的数据：发出之前收到的数据证明不了之后的连接状态。

默认用 WebSocket 协议层的 ping 帧（交给 OkHttp 的 `pingInterval`），服务端按协议自动应答，不需要任何业务配合。
服务端主动发心跳、要求客户端应答的协议用 `autoReply`。

### 重连计数在连接稳定后才清零

如果在连上的那一刻就清零，"能连上但马上被踢"（鉴权失败、服务端过载保护）会让退避永远停在第一档，
客户端以最小间隔无限重连。所以连接保持 `stableAfter`（默认 10 秒）之后断开才重新计数。

退避带随机抖动，避免服务端重启后所有客户端在同一时刻连回来。

### url 是函数

每次连接前调用一次。可以在这里换线路（配合 AutoHost）、带上新的签名或时间戳。

## 边界行为

- 握手未完成时 `disconnect()`：直接取消连接，不走关闭握手。
- 服务端发起关闭：回 close 帧完成握手，同时立刻按断开处理，不等 `onClosed`（对端不配合的话 OkHttp 要 60 秒后才回调）。
- 订阅消息发送失败：发 `SendFailed` 事件，订阅仍然登记在册，下次重连后恢复。
- 接入方提供的回调（`topicOf`、`autoReply`、`binaryDecoder`、`greeting`、url 函数、`configureRequest`、重连策略）抛异常：
  发 `CallbackFailed` 事件；消息仍会出现在 `messages` 里，url 和 `configureRequest` 出错按一次连接失败处理（走退避），
  策略出错按放弃重连处理。
- 收集者被取消时缓冲区里剩下的消息不算丢弃。
- `close()` 之后所有 Flow 正常结束，其余方法不再有效果；之后再 `subscribe` 得到的 Flow 立即结束。

## 工程形态

Android Library，minSdk 21，只依赖 OkHttp 和 kotlinx-coroutines。库本身没有用到 Android API，
目前以 AAR 发布是为了和消费方的工程保持一致的接入方式；拆成纯 JVM artifact 在路线图里。

OkHttp 隔在内部的 `Transport` 接口后面。状态机的单测用假的传输层和协程虚拟时间，
另有一组基于 MockWebServer 的集成测试走真实的 OkHttp 链路。
